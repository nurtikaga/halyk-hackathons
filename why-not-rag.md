# Архитектурное решение: почему мы отказались от RAG

## TL;DR

Первым инстинктом было построить классический RAG-пайплайн: разбить все документы на чанки, embedding, векторная база, semantic search. После вдумчивого анализа реальной структуры датасета мы отказались от этого подхода в пользу **детерминированной связки по точному ключу** (`account_id`). Результат: **100% recall** вместо вероятностного, **нулевая стоимость** отбора вместо инфраструктуры embeddings, и на порядок меньше токенов в каждом вызове LLM.

Ниже — весь ход рассуждений, как мы к этому пришли.

---

## 1. Почему RAG казался очевидным выбором

Формулировка задачи звучит как классический RAG-кейс:

> «Агенту предстоит разобраться в архиве из десятков PDF-документов и реестра транзакций... находить нужные/актуальные версии документов, отличая их от устаревших... извлекать скрытые факты»

«Найди релевантное среди многого» — это ровно то, для чего в индустрии обычно тянут RAG: embeddings, векторная база, top-K retrieval. Мы начали с этого же допущения.

## 2. Что изменилось, когда мы посмотрели на реальные данные

Вместо того чтобы сразу писать embedding-пайплайн, мы сначала **прочитали сам датасет руками** — и структура данных оказалась совсем не "найди иголку в стоге сена по смыслу".

### 2.1. Леджер транзакций содержит явный ключ

```
txn_id,date,account_id,counterparty,description,amount,currency
TXN-B1-0020,2025-03-15,ACC-7201,...,...,-45000.00,USD
```

`txn_id` устроен как `TXN-{scenario_id}-{seq}` — **scenario_id читается напрямую из идентификатора транзакции**, без всякого поиска "по смыслу". Один regex:

```python
df['scenario_id'] = df['txn_id'].str.extract(r'^TXN-([A-Z0-9]+)-')
```

### 2.2. Каждый account_id соответствует РОВНО одному сценарию

Мы проверили это на всём леджере (1473 транзакции) — связка `account_id ↔ scenario_id` строго 1:1, без единого исключения:

| Наблюдение | Значение |
|---|---|
| Всего транзакций в леджере | 1473 |
| Всего scenario-префиксов в леджере | 561 |
| Реально нужных сценариев (есть в шаблоне ответа) | 12 |

**561 против 12** — то есть 549 «сценариев» в леджере оказались намеренно подмешанным шумом/дистракторами, не имеющим отношения к задаче. Это подтвердило: датасет специально спроектирован так, чтобы проверить, отличит ли агент релевантное от нерелевантного — но проверяется это точным ключом, а не векторным поиском.

### 2.3. account_id встречается в тексте PDF буквально

Каждый кредитный договор содержит в тексте свой `account_id` (например, в реквизитах на последней странице: `«Account ACC-7805»`). Значит, связку «какой документ относится к какому сценарию» можно построить **точным совпадением строки**, а не оценкой семантической близости.

### 2.4. Организаторы сами описали именно этот механизм

В официальном описании задачи (`CASE.md`) прямым текстом:

> «Связывает их леджер: ID каждой транзакции начинается с `scenario_id`... Каждый `account_id` соответствует ровно одному `scenario_id`»

Это не наша интерпретация — это описанный организаторами способ связки. RAG здесь не требуется по постановке задачи.

---

## 3. Сравнение подходов

| | Точное совпадение (наш выбор) | RAG / semantic search |
|---|---|---|
| Единица отбора | Целый документ | Чанк (200–500 слов, произвольные границы) |
| Механизм отбора | Точное совпадение по ключу (`account_id` в тексте) | Косинусная близость embedding'ов |
| Гарантия полноты | 100% — если ключ есть в файле, он гарантированно найдётся | Нет гарантии — нужный чанк может не попасть в top-K |
| Инфраструктура | Ничего, кроме `regex` и `pandas` | Embedding-модель, векторная БД, логика чанкинга |
| Стоимость отбора | $0 | Embedding-вызовы + инфраструктура |
| Что видит LLM | Весь текст релевантных документов целиком | Только выбранные фрагменты без соседнего контекста |

## 4. Конкретный пример, почему это не абстрактный спор

При разборе сценария **B1** мы нашли переломный для решения кейс. В финальном (не черновом) аудиторском отчёте была фраза:

> «Сумма в размере $592,296.10, выплаченная контрагенту Irtysh Advisory Bureau, первоначально учтённая как Консультационные услуги, переклассифицирована для целей соблюдения ковенантов как Процентные расходы»

Это единственный абзац во всём документе, который объясняет, почему коэффициент покрытия процентов у заёмщика упал ниже порога 2.00x (BREACH вместо COMPLIANT).

**При точном совпадении по `account_id`:** этот абзац гарантированно попадает в промпт LLM — мы заранее знаем, что весь файл относится к нужному заёмщику, весь текст передаётся целиком.

**При RAG:** пришлось бы формулировать запрос для embedding-поиска заранее — но мы **не знаем заранее**, что искать, пока не прочитали документ. Реального «вопроса», под который этот чанк гарантированно попал бы в top-K, не существует. Если бы чанк не попал в выборку — ответ был бы неверным не из-за ошибки модели, а из-за того, что нужный текст до неё физически не дошёл.

## 5. Итоговая архитектура

```
run.py
 │
 ├─ ledger.py     → account_id ↔ scenario_id из леджера, фильтрация 561 → 12 нужных
 ├─ ingest.py      → извлечение текста всех PDF (pdfplumber + дисковый кэш)
 ├─ classify.py    → БЕЗ LLM, регулярками:
 │                    • тип документа (contract / audit / kyc)
 │                    • действующая редакция vs «НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ»
 │                    • финальная позиция аудитора vs черновик
 │                    • текст пунктов 6.1/6.2/6.3 из действующего договора
 ├─ reason.py      → ОДИН вызов LLM на сценарий: вырезанные пункты ковенантов +
 │                    финальные аудит/KYC документы + отфильтрованные по периоду
 │                    транзакции → status/actual/evidence_txn_id по каждому ковенанту
 └─ validate.py    → локальный скоринг против ground_truth.json
```

### Дополнительные находки, подтвердившие правильность подхода

При ручном разборе документов до написания кода мы нашли ещё два «капкана», намеренно заложенных в датасет:

- **Устаревшие редакции договора** — помечены `«НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ ... НЕ ПРИМЕНЯЕТСЯ»`. Есть у части сценариев (например, у B1 — 2 версии договора).
- **Черновики аудиторских отчётов** — помечены `«ПРОЕКТ — ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ ... НЕ ЯВЛЯЕТСЯ ОКОНЧАТЕЛЬНОЙ ПОЗИЦИЕЙ АУДИТОРА»`.

Оба маркера — явный, регулярно повторяющийся текст, который надёжно ловится regex'ом **до** отправки в LLM. Это ещё раз подтвердило: задача проверяет умение работать со структурой и версионностью документов, а не способность к нечёткому семантическому поиску.

---

## 6. Что мы получили в итоге

- **Ноль ошибок связки** документ ↔ сценарий на всех 12 сценариях открытого датасета
- **~15–30 тыс. символов на вызов LLM** (вырезанные пункты + 2–3 supporting-документа) вместо необходимости прогонять по 200 файлов
- **Полная прослеживаемость** — каждый ответ агента опирается на текст, который гарантированно был показан модели, а не на вероятностно найденный фрагмент
- **Простая, дешёвая, объяснимая инфраструктура** — без embedding-моделей, без векторной БД, без параметров чанкинга, которые пришлось бы подбирать вслепую

RAG остаётся правильным инструментом для задач, где заранее неизвестно, в каком из многих документов искать. В этой задаче организаторы дали точный детерминированный ключ связки — и использовать его напрямую оказалось надёжнее, дешевле и точнее, чем оборачивать точную задачу в вероятностный инструмент.
