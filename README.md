# Halyk AI Challenge — агент по проверке ковенантов

Читает PDF-договоры + аудит/KYC-документы + реестр транзакций и для каждого
ковенанта (6.1/6.2/6.3) каждого заёмщика определяет `status`, `actual`,
`evidence_txn_id`. Формат вывода — точно `submission_template.json`.

## Провайдеры LLM

Пайплайн поддерживает несколько провайдеров через один и тот же код (`src/reason.py`) - переключение только через `.env`, без правки кода:

| Провайдер | Что задать в `.env` | Автоопределение |
|---|---|---|
| Anthropic API | `ANTHROPIC_API_KEY`, `HALYK_AGENT_MODEL=claude-fable-5` (или другая) | По умолчанию, если ниже ничего не задано |
| TokenRouter (tokenrouter.com) | `TOKENROUTER_API_KEY`, `HALYK_AGENT_MODEL=<id модели из вашего кабинета>` | Автоматически при наличии `TOKENROUTER_API_KEY` |
| OpenRouter (openrouter.ai) | `OPENROUTER_API_KEY`, `HALYK_AGENT_MODEL=moonshotai/kimi-k3` (с `/`) | Автоматически при наличии `OPENROUTER_API_KEY` + `/` в имени модели |
| Любой другой OpenAI-совместимый шлюз | `HALYK_API_BASE_URL`, `HALYK_API_KEY` | Автоматически, если задан `HALYK_API_BASE_URL` |

**Важно про TokenRouter:** точный ID модели (например, `kimi-k3` vs `moonshotai/kimi-k3` vs что-то ещё) зависит от того, как настроен ваш кабинет на tokenrouter.com - посмотрите список доступных моделей в своём Console на сайте и впишите точное имя оттуда в `HALYK_AGENT_MODEL`. Неверное имя даст ошибку "model not found" при первом вызове.

## Как это устроено (пайплайн, без LLM в горячем пути где не нужно)

```
run.py
 ├─ src/ledger.py    → леджер: account_id ↔ scenario_id (через префикс TXN-{scenario}-...)
 ├─ src/ingest.py     → извлечение текста PDF, дисковый кэш (не парсим одно и то же дважды)
 ├─ src/classify.py   → БЕЗ LLM, регулярками:
 │                        - тип документа (contract / audit / kyc)
 │                        - устаревшая редакция договора ("НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ")
 │                        - черновик аудита ("ПРОЕКТ — ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ")
 │                        - текст пунктов 6.1/6.2/6.3 из действующего договора
 ├─ src/reason.py     → ЕДИНСТВЕННЫЙ вызов LLM (claude-fable-5) на сценарий:
 │                        получает вырезанные пункты ковенантов + финальные
 │                        аудит/KYC документы + отфильтрованные транзакции периода,
 │                        возвращает structured JSON с 3 ковенантами
 └─ src/validate.py   → локальный скоринг против ground_truth.json (точно по
                          формуле из CASE.md), для проверки на открытых 12 сценариях
```

Почему не векторный RAG и не LangChain: документы хорошо структурированы
("Статья 6", "Пункт 6.N"), поэтому нарезка регулярками надёжнее и на порядок
дешевле по токенам, чем семантический поиск. LLM видит только релевантный,
уже вырезанный текст — не весь 15-страничный договор.

Транзакции (`master_ledger_2025.csv`) не индексируются в векторную базу —
это структурированные табличные данные, фильтруются через `pandas` по
`account_id` и датам ковенантного периода.

## Важно про датасет (уже проверено на открытых 200 PDF)

- В леджере 1473 строки, но только 12 scenario-префиксов реально нужны
  (совпадают с ключами `submission_template.json`); остальные ~549 — шум,
  пайплайн их автоматически отсекает через `build_account_scenario_map`.
- У части заёмщиков есть 2 версии договора — старая помечена
  "НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ ... НЕ ПРИМЕНЯЕТСЯ", код её игнорирует.
- У части аудиторских отчётов есть черновая/промежуточная версия
  ("ПРОЕКТ — ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ ... НЕ ЯВЛЯЕТСЯ ОКОНЧАТЕЛЬНОЙ ПОЗИЦИЕЙ
  АУДИТОРА") — тоже отфильтровывается, в LLM идёт только финальная позиция.
- Все 200 PDF в открытом датасете — текстовые (не сканы), OCR не понадобился
  ни разу. `src/ingest.py::_ocr_fallback` — заглушка на случай сканов в
  приватном датасете; если такие появятся, нужно будет её дописать
  (pytesseract или отправка страницы как изображения в API).

## Запуск

### Вариант 1 — Docker (рекомендуется для передачи другим / судьям)

Не нужно ставить Python/зависимости вручную — только Docker.

```bash
# 1) Положить рядом с docker-compose.yml:
#    - .env (свой ANTHROPIC_API_KEY, см. .env.example)
#    - папку agentic-bank-public/ (датасет от организаторов)

# 2) Проверка без трат токенов:
docker compose run --rm agent --dry-run

# 3) Полный прогон:
docker compose run --rm agent

# Результат появится на хосте в ./output/submission.json

# 4) Локальный скоринг (тот же контейнер, другая команда):
docker compose run --rm agent python src/validate.py \
    --submission /app/output/submission.json \
    --ground-truth /app/data/ground_truth.json
```

Датасет монтируется как read-only volume (`agent` его не может случайно
испортить), кэш распарсенных PDF переживает перезапуски контейнера
(`./cache` на хосте), результат пишется напрямую на хост в `./output/`.

Для приватного датасета 9 августа — просто заменить содержимое
`agentic-bank-public/` (или указать другой путь в `docker-compose.yml`),
пересобирать образ не нужно.

### Вариант 2 — локально (Python)

```bash
pip install -r requirements.txt
cp .env.example .env   # вписать свой ANTHROPIC_API_KEY
export $(cat .env | xargs)

# 1) Разложить открытый датасет рядом (папка должна называться agentic-bank-public
#    и содержать master_ledger_2025.csv, documents/, ground_truth.json,
#    submission_template.json — как раздали организаторы)

# 2) Проверка "сантехники" без трат токенов:
python run.py --dataset agentic-bank-public --output submission_dryrun.json --dry-run

# 3) Полный прогон с LLM:
python run.py --dataset agentic-bank-public --output submission.json

# 4) Локальная проверка качества на открытых 12 сценариях:
python src/validate.py --submission submission.json --ground-truth agentic-bank-public/ground_truth.json
```

Для приватного датасета (9 августа) — те же команды, просто `--dataset`
указывает на новую папку. Код не меняется, только входные данные.

## Известные ограничения / TODO

- `_ocr_fallback` в `src/ingest.py` не реализован — доделать, если в
  приватном датасете окажутся сканы.
- Финальную арифметику (например, коэффициент EBITDA/проценты по данным
  из "Примечаний к финансовой отчётности") делает LLM, а не детерминированный
  код — потому что нужные цифры не структурированы (лежат внутри
  прозы аудиторского отчёта). `reasoning` в ответе модели явно фиксирует,
  какие числа и формулу она использовала — это можно аудировать глазами
  при разборе ошибок после локального скоринга.
- Если после `validate.py` видите систематическую ошибку на конкретном типе
  ковенанта — исправлять стоит промпт в `src/reason.py`, а не постфактум
  трогать сырые ответы.

## Бюджет токенов

На открытых 12 сценариях промпт на сценарий — 20-30 тыс. символов (~7-9 тыс.
токенов), потому что в LLM передаются только пункты ковенантов + финальные
аудит/KYC документы + отфильтрованный список транзакций, а не весь архив.
Перед прогоном на приватном датасете стоит повторно прикинуть бюджет исходя
из фактического числа сценариев/документов.
